SEMANTIC EDITS
==============

Keep edits within the user's requested scope. A preview-only request does not
authorize applying changes. Follow an implementation request through its
authorized edits and validation without adding a separate approval step.

RENAME A SYMBOL
---------------
1. Request a preview at a one-based symbol position:
edit {"action":"rename","symbol":"Calculator.Add","newName":"Compute"}

A symbol name replaces file, line and character, as in navigation.txt.
code_actions also accepts symbol. A selection still needs file and positions.

2. Read the changed files and edits. Apply the returned proposalId:
edit {"action":"rename","proposalId":"ID_FROM_PREVIEW","apply":true}

RENAME A FILE
-------------
newName is a workspace-relative destination, not a symbol name:
edit {"action":"rename_file","file":"src/Calculator.cs","newName":"src/Math/Calculator.cs"}

Apply its proposalId with the edit tool, action rename_file and apply true.
This requires Roslyn to advertise file rename support.

FIXES AND REFACTORINGS
---------------------
1. List actions at the diagnostic or selected code:
edit {"action":"code_actions","file":"src/Calculator.cs","line":12,"character":9}

For a selection, also pass endLine and endCharacter, both one-based.
Available actions depend on the installed Roslyn version and loaded project.

2. Choose an action from the returned listing. Resolve its preview using the
listing's proposalId and the action's zero-based index:
edit {"action":"code_actions","proposalId":"ID_FROM_LISTING","actionIndex":0}

3. Inspect the preview. Apply its NEW proposalId:
edit {"action":"code_actions","proposalId":"ID_FROM_PREVIEW","apply":true}

Do not reuse the listing ID in place of the resolved preview ID.
Some command-based actions reveal their edits only during execution.

A listing starts with "proposal ID", then one line per action: its zero-based
index, its kind when Roslyn gives one, and its title:
0 quickfix using System.Collections.Generic;

A preview starts with "proposal ID: N files, not applied". Each file operation
follows (change, create, delete, or rename OLD -> NEW), then its excerpts:
@@ 12:9
- int Add(int a, int b)
+ int Compute(int a, int b)
@@ gives the one-based start of the excerpt, followed by "-> LINE:CHARACTER"
when the start differs in the new text. Excerpts keep some unchanged context.
"preview truncated:" marks an incomplete view of the changes.
The preview is limited to 32 000 characters. "truncated: N of M files shown"
marks omitted files, and "command omitted" an omitted command description.
These display limits do not change the edit stored by proposalId.

PROPOSAL LIFETIME AND FAILURES
------------------------------
Proposals expire after five minutes. Reload discards them.
On stale_edit, request a new preview against current files. Do not retry the old ID.
After applying, inspect the result and rerun diagnostics on affected files.
File creation, deletion and renaming trigger a Roslyn reload before the next request.

An application result starts with a status line, then one line per completed
file operation, in order:
applied: 2 files, 2 operations, Roslyn synchronized
change src/Calculator.cs
change src/Program.cs
The status is applied, partially applied or not applied. "Roslyn synchronized"
reports a successful Roslyn refresh. Commands add "command executed" and their
result. On a later failure, the response starts with "error CODE: message" and
"failed step: STEP", with the failed path and operation when known, and then
the receipt. Read both before retrying. The next request reloads Roslyn after
an application failure. Large receipts end with "truncated: N more operations
not shown" or "result omitted".

Edits must remain inside the workspace. Symlinks below its root are rejected.
Each file replacement is atomic. A failed multi-file operation can leave partial
changes, so inspect the workspace before retrying.
Limits: 256 edited files, 8 MiB per file, 64 MiB total edited content,
and 256 MiB for the source snapshot used to detect stale edits.
